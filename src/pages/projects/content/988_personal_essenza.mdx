## Resumen general

Essenza es un SaaS multi-tenant para tiendas de perfumes: cada negocio tiene su tienda pública y su panel de administración, y todos comparten una sola API y una sola base de datos. El aislamiento entre negocios lo garantiza PostgreSQL, no solo el código.

**Qué se construyó**

- **Tienda:** Astro con renderizado en servidor (SSR) sobre un Cloudflare Worker, pensada para SEO.
- **Backoffice:** React + TypeScript + Vite con Tailwind CSS.
- **API:** Go con Fiber y arquitectura hexagonal.
- **Base de datos:** PostgreSQL 17 en Neon, con Row Level Security para aislar a cada tenant.

**Cómo se validó**

- SonarQube sobre los tres proyectos (API, tienda y backoffice).
- OWASP ZAP sobre la API, el backoffice y la tienda.
- k6 para carga, con la API limitada como en Render Free (0.1 CPU y 512 MB).
- Vitest y Playwright (572 tests de Vitest en la tienda y 714 en el backoffice, al 2026-11-21).

**Dónde está desplegado**

- Neon: base de datos y, en un segundo proyecto, el almacenamiento de imágenes.
- Render: la API (Web Service con Docker) y el backoffice (Static Site).
- Cloudflare: la tienda como Worker.
- Brevo: correo transaccional por HTTPS.

## Tienda (Storefront)

Astro con renderizado en servidor sobre un Cloudflare Worker (uno por negocio). Prioridad: SEO y páginas ligeras. Los cambios del backoffice se ven sin reconstruir ni volver a desplegar la tienda.

### Qué se hizo

- Landing, categorías (`/categoria/<slug>/`) y página de producto, cada una con una URL real, canónica propia, `sitemap.xml` dinámico y un 404 con estado real y sugerencias.
- Páginas livianas: la landing muestra 12 tarjetas por sección y un paginador numerado ("Página N de M"); los productos que no caben viven en `/categoria/<slug>/?pagina=N`.
- Filtros sobre todo el catálogo (género, marca, precio, exclusivos, orden) como un formulario GET que funciona sin JavaScript. Con JavaScript, el paginador y los filtros cambian solo el bloque necesario.
- Producto con galería de hasta 5 fotos con zoom, presentaciones por tamaño, etiqueta "Agotado" (la API nunca expone la cantidad) y reseñas en un modal sin captcha.
- Mapa de Google solo si el negocio configuró su ubicación, logos de la marca traídos de la API (con respaldo local), imagen para compartir y datos estructurados JSON-LD.
- Carrusel de reseñas, seguimiento de visitantes con id persistente (respeta DoNotTrack) y una caché en el borde que la API purga después de cada escritura.

### Decisiones técnicas

- **SSR en un Worker en vez de un sitio estático.** Los dueños editan productos desde el backoffice; un sitio estático pediría reconstruir cada vez. A cambio, el Worker tiene límites de CPU y de subpeticiones y depende de la caché para ser rápido (la CPU real en el plan gratuito no se midió).
- **Caché de borde con "generación" de purga.** La Cache API no puede borrar todo; subir un número en la clave deja huérfanas todas las entradas. Pero la caché de Cloudflare es por centro de datos: el que recibe la purga se limpia al instante y el resto converge por TTL, hasta 5 minutos.
- **TTL cortos y distintos.** Páginas 300 s, listados filtrados 60 s, 404 30 s, y el navegador siempre revalida (`max-age=0`).
- **Clave de caché normalizada.** Solo entran `pagina`, `tamano` y los filtros, en minúscula y en orden fijo; así `utm_*` y `fbclid` comparten la entrada limpia. Un valor inválido responde 302 a la URL normalizada.
- **Una sola renderización por URL fría** (`src/middleware.ts`). Si muchos visitantes piden a la vez la misma página sin caché, uno renderiza y los demás esperan. Solo vale por instancia del Worker.
- **Páginas livianas y paginación en servidor.** Con 300 productos la landing pesaba 1.27 MB de HTML; ahora unos 142 KB, y la página de producto bajó de 153 KB a 34 KB. A cambio, los productos de más allá de la primera página viven en otra URL.
- **Filtros con `noindex,follow` y canónica al listado sin filtrar.** Los filtros no diluyen el SEO ni llenan el sitemap. La lista sin filtros sí se indexa y su página N es canónica de sí misma.
- **Mejora progresiva.** Cada círculo del paginador y el botón "Filtros" son enlaces reales; si el script falla, se navega normal. El costo es mantener dos caminos por control.
- **Sin captcha en las reseñas.** Se quitó Cloudflare Turnstile de punta a punta. El spam se frena con un honeypot, un límite por IP en la API y moderación en el backoffice; el dueño aceptó una protección más débil.
- **CSP estricta sin `unsafe-inline` en scripts.** Astro calcula hashes SHA-256 de los scripts y estilos inline; el Worker añade los orígenes exactos de imágenes, API y mapa. Queda `style-src-attr 'unsafe-inline'` porque los atributos `style=""` no se pueden hashear.
- **Datos por petición, sin caché en memoria.** Cada petición pide sus datos una sola vez y no los guarda; la única caché es la del borde.
- **Sin dominio propio.** La tienda vive en `workers.dev`, así que `PUBLIC_SITE_URL` debe coincidir exactamente con esa URL; que la Cache API funcione en `workers.dev` no está confirmado.

### Pruebas

#### SonarQube (proyecto `frontoffice-saas-stores`)

**Pruebas antes (hallazgos).** 2026-11-21, reglas "Sonar way": 13 issues abiertos (3 bugs, 2 vulnerabilidades, 8 code smells), fiabilidad D y seguridad C. Los más serios: 6 regex con retroceso que podían colgar el servidor con entradas largas (`S8786`), un `sort()` sin comparador (`S2871`), una Promise usada como condición, siempre verdadera, en el carrusel de reseñas (`S6544`) y generadores pseudoaleatorios para los ids de visita (`S2245`).

**Correcciones.**
- 11 se corrigieron con código: las 6 regex pasaron a recortes lineales en `src/lib/text.ts` (con un test que las compara contra la regex original, incluida una entrada de 100 000 barras); un comparador explícito que mantiene el orden por unidad de código, para no cambiar las URLs canónicas; la condición del carrusel ahora mira `document.fonts`; `Number.NaN`; ids con `crypto.getRandomValues`; y un `try/catch` inútil fuera.
- 2 no se corrigieron: son excepciones justificadas en `sonar-project.properties`. La regex del correo (la entrada se limita a 254 caracteres y Sonar sigue marcando la forma) y un `Math.random` como último recurso cuando no existe `crypto` (ids de analítica, nunca secretos). Una excepción esconde el aviso, no lo arregla.
- En una pasada intermedia (segunda ronda) quedaban 2 abiertos, ambos `S2245`.

**Pruebas después (resultados).** 13 a 0 abiertos, fiabilidad D a A y seguridad C a A, con 572 tests de Vitest en 44 archivos y `astro check` sin errores ni avisos. El Quality Gate pasó de OK a ERROR solo por la cobertura del código nuevo (0 % contra un mínimo de 80 %): la cobertura no se mide porque no se envía ningún reporte de tests a Sonar. El detalle de los security hotspots no se pudo leer con el token de análisis (el conteo es 0).

#### OWASP ZAP (ZAP 2.17.0, build de producción)

**Pruebas antes (hallazgos).** 2026-11-21: 3 alertas Medium de CSP (comodín, `script-src` y `style-src` con `unsafe-inline`), 1 Low real (`nosniff` ausente en los archivos de `/_astro/*`) y 1 Low más 5 informativas, que son falsos positivos o avisos. En total 2 problemas reales, ambos de cabeceras. No hubo inyección ni XSS; la alerta de posible XSS se probó a mano y Astro escapa el parámetro. Además, 3 tests de Playwright fallaban (con y sin ZAP): scroll horizontal en el teléfono, la hoja de filtros de la landing y `?orden=zzz&genero=zzz` que daba 200 en vez de 302. Pasaban 33, fallaban 3 y se omitía 1.

**Correcciones.**
- Ronda 1: CSP con `default-src`, `script-src`, `style-src`, `img-src`, `connect-src`, `font-src` y `frame-src` en `security-headers.ts` (con tests) y `nosniff` para `/_astro/*` en `public/_headers` (`fdf9e11`).
- Ronda 2: CSP nativa de Astro con hashes SHA-256 y `img-src` limitado al origen del bucket de imágenes (`7453566`).
- En la misma ronda: las URLs largas del FAQ ensanchaban la página en el teléfono (`overflow-wrap` y `min-width: 0`) y la caché servía una página con valores inválidos en vez de redirigir (ahora se salta la caché para esas URLs, con test).

**Pruebas después (resultados).** Sin alertas Medium y sin la alerta de `nosniff`. Queda 1 Low (una constante numérica dentro del JS del hero, falso positivo) y 3 informativas de la tienda, más 2 informativas de la API pública vista desde la tienda. Playwright a través de ZAP pasó de 33 / 3 / 1 a 36 / 0 / 1 (pasan / fallan / omitido). Límites: ZAP no analiza el DOM, el preview local no pasa por Cloudflare (las cabeceras de borde pueden diferir) y la autorización por rol y tenant no está cubierta.

## Backoffice

Panel de administración en React + TypeScript + Vite, con diseño propio sobre Tailwind. Se despliega como Render Static Site y habla con la API por HTTPS.

### Qué se hizo

- Secciones con registro único (rutas, menú y migas) y permisos por rol que vienen de la API.
- Productos con tipo y 1 a 20 presentaciones (tamaño, precio y stock privado), hasta 5 fotos y reordenado arrastrando.
- Generador de catálogo en PDF/PNG en el navegador, con 3 a 5 productos por fila y solo productos activos con stock.
- Datos del negocio con logo, ícono y wordmark por tenant; reseñas con moderación; FAQs, contactos y artículos.
- Panel con estadísticas por período y sección de visitantes; roles, usuarios y, para la plataforma, alta y baja de tenants.
- Flujo de recuperación de contraseña en 3 pasos y "Mi perfil".

### Decisiones técnicas

- Pantallas difíciles de probar → una `logic.ts` pura por sección (filtros, validación, payloads) probada con Vitest → 714 tests rápidos y sin DOM.
- Convertir fotos en la API gratuita tardaba ~1 min y agotaba la memoria → conversión a WebP en el navegador (1600 px, calidad 0.82) con cola secuencial → una subida válida responde en ~157 ms.
- API gratuita con poca CPU → TanStack Query con `staleTime` por área e invalidación según la escritura → menos peticiones repetidas y sin listas viejas tras guardar.
- Reordenar con una petición por fila era lento → orden optimista con un único `PUT .../order` y reversión si falla → respuesta inmediata.
- Catálogo sin servicio de renderizado → páginas A4 como DOM, `html-to-image` y `jsPDF` → PDF sin carga en el servidor (requiere CORS en el bucket).
- Permisos que solo ocultan botones → la UI oculta y la API vuelve a exigir cada permiso → sin depender de la interfaz.
- Riesgo de XSS robando la sesión → token en `sessionStorage` y CSP estricta con cabeceras → ZAP sin alertas Medium.
- Regex de correo copiada en 4 archivos → un solo `isEmailShape` con tope de 254 caracteres → una sola copia que mantener.

#### OWASP ZAP (build de producción servido con `vite preview`)

ZAP no puede descubrir las rutas de una SPA con la araña, así que se recorrió con Playwright pasando por el proxy de ZAP.

- **Pruebas antes (hallazgos), 2026-11-21:** 6 alertas distintas. 3 reales: CSP ausente (Medium), sin anti-clickjacking (Medium) y sin `nosniff` (Low). ## API

API en Go con Fiber, arquitectura hexagonal por feature y PostgreSQL (Neon) con Row Level Security. Corre en Render (plan gratuito: 0.1 CPU y 512 MB), con la base en Neon y el correo por la API HTTPS de Brevo.

### Qué se hizo

- Una carpeta por feature con casos de uso que no conocen a Fiber, pgx ni AWS; un test de arquitectura verifica las reglas de capas.
- Aislamiento por tenant con RLS forzado y un rol `app_api` sin propiedad de tablas ni `BYPASSRLS`.
- Autenticación con JWT y sesión verificada en cada petición de admin, argon2id, roles y permisos, y superadmin de plataforma.
- Catálogo con tipos de producto y presentaciones, stock privado, reseñas anónimas, FAQs, contactos, artículos y estadísticas de visitantes.
- Imágenes validadas como WebP (máximo 5 por producto) y guardadas con clave única; borrado lógico en todo.
- Lecturas públicas con ETag, purga de la tienda tras cada escritura, límites de tasa y rechazo por sobrecarga.
- Validación: tests unitarios, de integración y de arquitectura, `go build`, `go vet`, SonarQube, OWASP ZAP y k6 con los límites de Render.

### Decisiones técnicas

- El aislamiento no debía depender de recordar un `WHERE tenant_id` → RLS con `FORCE` y claves foráneas compuestas `(tenant_id, x_id)` → la base rechaza el cruce entre tenants.
- Un rol creado en la consola de Neon hereda `BYPASSRLS` → el rol se crea con SQL y se comprueba `rolbypassrls = false` → el aislamiento no se apaga en silencio.
- Un JWT sin estado no cierra sesión al cambiar la contraseña → chequeo de sesión (permisos, `pwd`, tenant activo) en cada petición de admin → el cierre es inmediato.
- La arquitectura se degrada sin que nadie lo note → test de arquitectura que falla ante una violación → las reglas se cumplen en CI.
- "No se borra nada" → `deleted_at` y `DELETE` revocado en las últimas tablas → la base rechaza el borrado físico.
- Dos subidas simultáneas podían pasar el límite de 5 fotos → recuento bajo `FOR UPDATE` → el límite se mantiene.
- El login costaba 3.6 s de CPU en 0.1 CPU → argon2id al mínimo de OWASP en un pool acotado → 0.7 s por login y 503 inmediato si la cola se llena.
- Render bloquea los puertos SMTP → correo por la API HTTPS de Brevo → recuperación de contraseña y reenvío de invitaciones funcionando.
- Lecturas repetidas sobre una API de 0.1 CPU → `ETag` con 304 y `s-maxage=30` más 60 s de `stale-while-revalidate` → menos trabajo para el origen.
- Ráfagas con Neon detrás de un pooler → `QueryExecModeExec` sin sentencias preparadas en el servidor → funciona con pgbouncer.

## Cloud e infraestructura

Todo corre sobre planes gratuitos, con un runbook escrito en lugar de Terraform: son unos cinco recursos que se crean una sola vez, el plan gratuito de Render no se puede crear con su proveedor de Terraform y los proveedores de Neon estaban archivados o en beta (revisado el 2026-11-12).

### Qué se hizo

- **Base de datos:** un proyecto de Neon con Postgres 17 en Ohio, con conexión por pooler para la API y conexión directa para las migraciones.
- **Imágenes:** un segundo proyecto de Neon con Object Storage (compatible con S3, lectura pública). No es Cloudflare R2; las variables `R2_*` de la API conservan ese nombre por historia.
- **API:** Render Web Service con Docker, plan gratuito (0.1 CPU y 512 MB), en Ohio.
- **Backoffice:** Render Static Site. **Tienda:** Cloudflare Worker desplegado desde Git.
- **Correo:** Brevo por HTTPS, sin dominio propio: todo vive en subdominios de Render y Cloudflare.
- No hay workflows de GitHub Actions: Render y Cloudflare construyen directo desde los repositorios.

### Decisiones técnicas

- **Runbook en vez de Terraform:** el despliegue queda documentado paso a paso. A cambio, no es reproducible desde código.
- **Rol de base de datos creado con SQL:** un rol creado desde la consola de Neon hereda `BYPASSRLS` y apagaría el aislamiento sin avisar. Se crea con SQL y se comprueba que `rolbypassrls` sea `false`.
- **Pooler para la API, conexión directa para migraciones:** el pooler no admite sentencias preparadas, por eso no se usan en la API.
- **Imágenes en un proyecto aparte:** Neon da 5 GB de salida de datos por proyecto, compartidos entre base e imágenes. Separarlas hace que un pico de tráfico solo afecte a las fotos. La base guarda solo la clave del objeto.
- **Correo con Brevo:** Render bloquea los puertos SMTP (25, 465 y 587), así que Gmail SMTP nunca funcionó allí. Brevo usa una API HTTPS y no necesita dominio. Con un remitente `@gmail.com`, Brevo reescribe el remitente visible a su dominio y es más probable que caiga en spam. La API de Gmail queda como alternativa, pero necesita dominio propio para publicar la app.
- **Caché por capas:** navegador (`max-age=0`, siempre revalida), Worker de Cloudflare (300 s en páginas, 60 s en listados filtrados, 30 s en 404), API (`s-maxage=30` más 60 s de `stale-while-revalidate`, con ETag y 304) e imágenes inmutables por un año gracias a claves únicas.
- **Purga limitada:** la API avisa a la tienda con `POST /__purge` tras cada escritura, pero la caché de Cloudflare es por centro de datos. La purga limpia el que la recibe y el resto converge por TTL, hasta 5 minutos.
- **Límites del plan gratuito:** la API duerme a los 15 minutos sin tráfico y tarda cerca de un minuto en despertar; se previó un ping a `/health` cada 5 minutos que no despierta a Neon. No hay registro de que ese ping esté activo.
- **Secretos solo donde se usan:** la API recibe únicamente el rol restringido, el secreto de purga vive solo en el Worker y las variables `PUBLIC_*` y `VITE_*` no llevan secretos.
- **Migraciones solo hacia adelante:** archivos goose compatibles hacia atrás, aplicados a mano antes de subir el código, para que el código nuevo y el viejo convivan.

## General overview

Essenza is a multi-tenant SaaS for perfume stores: each business gets its own public storefront and admin panel, and all of them share one API and one database. Isolation between businesses is enforced by PostgreSQL, not only by application code.

**What was built**

- **Storefront:** Astro with server-side rendering (SSR) on a Cloudflare Worker, built for SEO.
- **Back office:** React + TypeScript + Vite with Tailwind CSS.
- **API:** Go with Fiber and a hexagonal architecture.
- **Database:** PostgreSQL 17 on Neon, with Row Level Security to isolate each tenant.

**How it was validated**

- SonarQube on the three projects (API, storefront and back office).
- OWASP ZAP on the API, the back office and the storefront.
- k6 for load, with the API limited like Render Free (0.1 CPU and 512 MB).
- Vitest and Playwright (572 Vitest tests in the storefront and 714 in the back office, as of 2026-11-21).

**Where it is deployed**

- Neon: the database and, in a second project, the image storage.
- Render: the API (Web Service with Docker) and the back office (Static Site).
- Cloudflare: the storefront as a Worker.
- Brevo: transactional mail over HTTPS.

## Storefront

Astro with server-side rendering on a Cloudflare Worker (one per business). Priorities: SEO and light pages. Changes made in the back office show up without rebuilding or redeploying the storefront.

### What was built

- Landing, categories (`/categoria/<slug>/`) and product page, each with a real URL, its own canonical, a dynamic `sitemap.xml` and a real 404 status with suggestions.
- Light pages: the landing shows 12 cards per section and a numbered pager ("Page N of M"); products that do not fit live at `/categoria/<slug>/?pagina=N`.
- Filters over the whole catalog (gender, brand, price, exclusives, sort) as a GET form that works without JavaScript. With JavaScript, the pager and filters swap only the block that changes.
- Product with a gallery of up to 5 photos with zoom, size presentations, a "Sold out" badge (the API never exposes the count) and reviews in a modal with no captcha.
- A Google map only when the business set a location, brand logos fetched from the API (with a local fallback), a share image and JSON-LD structured data.
- Reviews carousel, visitor tracking with a persistent id (DoNotTrack respected) and an edge cache that the API purges after every write.

### Technical decisions

- **SSR on a Worker instead of a static site.** Owners edit products from the back office; a static site would need a rebuild each time. The cost: the Worker has CPU and subrequest limits and relies on the cache to be fast (real CPU on the free plan was not measured).
- **Edge cache with a purge "generation".** The Cache API cannot delete everything; bumping a number in the key orphans every entry. But Cloudflare's cache is per data center: the one that gets the purge is cleared at once and the rest converge by TTL, up to 5 minutes.
- **Short, different TTLs.** Pages 300 s, filtered listings 60 s, 404 30 s, and the browser always revalidates (`max-age=0`).
- **Normalized cache key.** Only `pagina`, `tamano` and the filters go in, lowercase and in a fixed order; so `utm_*` and `fbclid` share the clean entry. An invalid value answers 302 to the normalized URL.
- **One render per cold URL** (`src/middleware.ts`). If many visitors ask for the same uncached page at once, one renders and the others wait. It only holds per Worker instance.
- **Light pages and server-side pagination.** With 300 products the landing was 1.27 MB of HTML; now about 142 KB, and the product page went from 153 KB to 34 KB. The cost: products past the first page live at another URL.
- **Filters with `noindex,follow` and a canonical to the unfiltered list.** Filters do not dilute SEO or fill the sitemap. The unfiltered list is indexed and its page N is canonical to itself.
- **Progressive enhancement.** Every pager circle and the "Filters" button are real links; if the script fails, normal navigation takes over. The cost is keeping two paths per control.
- **No captcha on reviews.** Cloudflare Turnstile was removed end to end. Spam is held back by a honeypot, a per-IP limit in the API and moderation in the back office; the owner accepted weaker protection.
- **Strict CSP without `unsafe-inline` on scripts.** Astro computes SHA-256 hashes of inline scripts and styles; the Worker adds the exact origins for images, the API and the map. `style-src-attr 'unsafe-inline'` remains because `style=""` attributes cannot be hashed.
- **Per-request data, no in-memory cache.** Each request fetches its data once and keeps nothing; the only cache is the edge one.
- **No custom domain.** The storefront lives on `workers.dev`, so `PUBLIC_SITE_URL` must match that URL exactly; that the Cache API works on `workers.dev` is not confirmed.

## Back office

Admin panel in React + TypeScript + Vite, with its own design system on Tailwind. It is deployed as a Render Static Site and talks to the API over HTTPS.

### What was built

- Sections driven by a single registry (routes, menu and breadcrumb) and role permissions that come from the API.
- Products with a type and 1 to 20 presentations (size, price and private stock), up to 5 photos and drag-to-reorder.
- A PDF/PNG catalog generator in the browser, with 3 to 5 products per row and only active products with stock.
- Business data with a logo, icon and wordmark per tenant; reviews with moderation; FAQs, contacts and articles.

### Technical decisions

- Screens hard to test → a pure `logic.ts` per section (filters, validation, payloads) tested with Vitest → 714 fast tests with no DOM.
- Converting photos on the free API took ~1 min and ran out of memory → WebP conversion in the browser (1600 px, quality 0.82) with a sequential queue → a valid upload answers in ~157 ms.
- Free API with little CPU → TanStack Query with a per-area `staleTime` and invalidation by write → fewer repeated requests and no stale lists after saving.
- Reordering with one request per row was slow → optimistic order with a single `PUT .../order` and rollback on failure → instant response.
- Catalog without a rendering service → A4 pages as DOM, `html-to-image` and `jsPDF` → a PDF with no server load (needs CORS on the bucket).
- Permissions that only hide buttons → the UI hides and the API enforces every permission again → no reliance on the interface.
- XSS risk stealing the session → token in `sessionStorage` and a strict CSP with headers → ZAP with no Medium alerts.
- Email regex copied in 4 files → one `isEmailShape` capped at 254 characters → a single copy to maintain.

## API

Go API with Fiber, feature-first hexagonal architecture and PostgreSQL (Neon) with Row Level Security. It runs on Render (free plan: 0.1 CPU and 512 MB), with the database on Neon and mail through the Brevo HTTPS API.

### What was built

- One folder per feature with use cases that know nothing about Fiber, pgx or AWS; an architecture test checks the layer rules.
- Tenant isolation with forced RLS and an `app_api` role that owns no tables and has no `BYPASSRLS`.
- Authentication with JWT and a session checked on every admin request, argon2id, roles and permissions, and a platform superadmin.
- Catalog with product types and presentations, private stock, anonymous reviews, FAQs, contacts, articles and visitor stats.
- Images validated as WebP (at most 5 per product) and stored under a unique key; soft delete everywhere.
- Public reads with ETag, storefront purge after every write, rate limits and load shedding.
- Validation: unit, integration and architecture tests, `go build`, `go vet`, SonarQube, OWASP ZAP and k6 with the Render limits.

### Technical decisions

- Isolation should not depend on remembering a `WHERE tenant_id` → RLS with `FORCE` and composite foreign keys `(tenant_id, x_id)` → the database rejects cross-tenant references.
- A role created in the Neon console inherits `BYPASSRLS` → the role is created with SQL and `rolbypassrls = false` is checked → isolation cannot be switched off silently.
- A stateless JWT cannot sign out on a password change → session check (permissions, `pwd`, active tenant) on every admin request → sign-out is immediate.
- Architecture decays unnoticed → an architecture test that fails on a violation → the rules hold in CI.
- "Nothing is deleted" → `deleted_at` and `DELETE` revoked on the last tables → the database refuses a hard delete.
- Two simultaneous uploads could pass the 5-photo limit → count under `FOR UPDATE` → the limit holds.
- Login cost 3.6 s of CPU on 0.1 CPU → argon2id at the OWASP minimum in a bounded pool → 0.7 s per login and an immediate 503 if the queue is full.
- Render blocks SMTP ports → mail through the Brevo HTTPS API → password recovery and invitation resend working.
- Repeated reads on a 0.1 CPU API → `ETag` with 304 and `s-maxage=30` plus 60 s of `stale-while-revalidate` → less work for the origin.
- Bursts with Neon behind a pooler → `QueryExecModeExec` with no server-side prepared statements → works with pgbouncer.

## Cloud and infrastructure

Everything runs on free plans, with a written runbook instead of Terraform: there are about five one-off resources, Render's free plan cannot be created with its Terraform provider and the Neon providers were archived or in beta (checked 2026-11-12).

### What was built

- **Database:** one Neon project with Postgres 17 in Ohio, with a pooled connection for the API and a direct one for migrations.
- **Images:** a second Neon project with Object Storage (S3 compatible, public read). It is not Cloudflare R2; the API's `R2_*` variables keep that name for historical reasons.
- **API:** Render Web Service with Docker, free plan (0.1 CPU and 512 MB), in Ohio.
- **Back office:** Render Static Site. **Storefront:** Cloudflare Worker deployed from Git.
- **Mail:** Brevo over HTTPS, with no custom domain: everything lives on Render and Cloudflare subdomains.
- There are no GitHub Actions workflows: Render and Cloudflare build straight from the repositories.

![API service configuration on Render](/assets/img/projects/essenza/render-api-service-config.png)

### Technical decisions

- **Runbook instead of Terraform:** the deploy is documented step by step. The trade-off is that it cannot be reproduced from code.
- **Database role created with SQL:** a role created in the Neon console inherits `BYPASSRLS` and would silently switch isolation off. It is created with SQL and `rolbypassrls` is checked to be `false`.
- **Pooler for the API, direct connection for migrations:** the pooler does not support prepared statements, so the API does not use them.
- **Images in a separate project:** Neon gives 5 GB of data egress per project, shared between database and images. Splitting them means a traffic spike only affects photos. The database stores only the object key.
- **Mail with Brevo:** Render blocks SMTP ports (25, 465 and 587), so Gmail SMTP never worked there. Brevo uses an HTTPS API and needs no domain. With a `@gmail.com` sender, Brevo rewrites the visible sender to its own domain and spam placement is more likely. The Gmail API stays as an alternative but needs an owned domain to publish the app.
- **Layered cache:** browser (`max-age=0`, always revalidates), Cloudflare Worker (300 s on pages, 60 s on filtered listings, 30 s on 404), API (`s-maxage=30` plus 60 s of `stale-while-revalidate`, with ETag and 304) and images immutable for a year thanks to unique keys.
- **Limited purge:** the API tells the storefront with `POST /__purge` after every write, but Cloudflare's cache is per data center. The purge clears the one that receives it and the rest converge by TTL, up to 5 minutes.
- **Free-plan limits:** the API sleeps after 15 minutes without traffic and takes about a minute to wake; a `/health` ping every 5 minutes that does not wake Neon was planned. Nothing records that the ping is active.
- **Secrets only where they are used:** the API gets only the restricted role, the purge secret lives only on the Worker and the `PUBLIC_*` and `VITE_*` variables carry no secrets.
- **Forward-only migrations:** backward-compatible goose files applied by hand before shipping the code, so new and old code coexist.
