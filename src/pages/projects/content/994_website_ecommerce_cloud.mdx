## Resumen

Diseño de la arquitectura en la nube de un e-commerce sobre Azure y su aprovisionamiento como infraestructura como código con Terraform, organizado en tres repositorios por responsabilidad: aplicaciones, almacenamiento y analítica.

## Logros clave

- <strong>Arquitectura completa justificada</strong> componente por componente: dos UI (FrontOffice y BackOffice), una API compartida, base de datos OLTP, Blob Storage, caché y Datawarehouse.
- <strong>Procesamiento asíncrono</strong> con Queue Storage y Azure Functions para tareas que no requieren respuesta inmediata, como la confirmación de pedidos.
- <strong>Azure Cache for Redis</strong> para carrito, sesión y datos frecuentes, buscando una experiencia fluida.
- <strong>Datawarehouse y ETL</strong> con Azure Data Factory para el análisis estratégico del negocio.
- <strong>Infraestructura en Terraform</strong> separada en tres repositorios con responsabilidad única, referenciando recursos compartidos entre ellos.

## Stack

Azure (App Service, Queue Storage, Functions, SQL Database, Blob Storage, Cache for Redis, Data Factory), Terraform.

# Descripción del Sistema E-commerce
------------

- Infraestructura escalable y robusta en la nube.
- Gestión de operaciones de venta en línea.
- Soportar alto volumen de transacciones.
- Proporcionar experiencia de usuario fluida a través de un portal principal.
- Permitir la gestión interna de productos y pedidos desde un BackOffice.
- Ofrecer capacidades analíticas avanzadas sobre los datos de venta para la toma de decisiones estratégicas.
- Plataforma capaz de manejar tareas intensivas o que no requieren una respuesta inmediata al usuario de forma eficiente en segundo plano.
- Asegurar que la experiencia de usuario no se vea afectada por procesos de larga duración, como confirmación de pedidos, actualización de inventarios complejos o generación de notificaciones masivas.

# Diseño de la Solución 

![Diagrama Arquitectura](/assets/img/projects/infra-ecommerce/Arquitectura_Nube_Ecommerce.drawio.png)

## Justificación de los componentes arquitectónicos

- **Dos WebServer para UI**. Separar responsabilidades entre un FrontOffice, BackOffice, y mejorar la seguridad.
- **DB SQL OLTP**. Alojar la información transaccional del negocio.
- **BLOB Storage.** Almacenar contenido estático y todos los archivos multimedia del negocio.
- **Webserver para API.** Maneja el acceso a los almacenamientos de datos del negocio. Una API compartida por ambas UI, ya que la UI del negocio no exige un costo computacional tan grande como para realizar una API única.
- **Queue Storage y Azure functions.** Manejar tareas en segundo plano y que no requieren respuesta inmediata, para evitar una alta carga de trabajo en el servidor que aloja la API.
- **Azure Cache for Redis.** Para alojar data frecuentemente visitada, carrito de compras, sesión del cliente, para lograr una UX fluida.
- **Azure Data Factory y DW**. Un orquestador para manejar el proceso ETL entre la DB OLTP del negocio y el Datawarehouse que guardará los datos listos para realizar análisis estratégico.

### Justificación más detallada del uso de los servicios (opcional)

- Cada tipo de usuario (clientes, editores) podrá acceder desde una **UI** en un servidor dedicado (**FrontOffice y BackOffice**).
- Las **UI** toman información de la **base de datos SQL** por medio de una única **API** (se ha decidido dejar una sola API, porque la gestión del negocio requiere de un costo computacional mucho menor que el realizado por los clientes).
- La UI de cliente prioriza la eficiencia y experiencia de usuario fluida, entonces la UI de cliente podrá enviar mensajes en **Queue storage** para pedidos, transacciones, etc., que luego serán ejecutadas en segundo plano por un **Serverless**.
- UI de cliente usará el **almacenamiento en caché (Azure Cache for Redis)** para alojar información como el carrito de compras, datos de sesión e información frecuentemente visitada, asegurando una **experiencia de usuario sin retardos**.
- Para el análisis de negocio se usa el **orquestador Data Factory**, para hacer el **proceso ETL** entre la **base de datos OLTP y el Datawarehouse**, para que luego la información del Datawarehouse pueda ser solicitada por la API o una herramienta externa (Power BI), y que la gestión del negocio pueda **realizar el análisis estratégico**.

# Código en Tres Repositorios Independientes
------------

Se ha decidido separar los recursos en módulos del negocio, en tres repositorios diferentes:

- Módulo de aplicaciones 
- Módulo de almacenamiento
- Módulo de analítica

Al descubrir que se puede optar por compartir recursos (e.g. servicio de base de datos puede ser compartido por la base de datos DW y OLTP, servicio de cuentas de almacenamiento puede ser compartido por Queue Storage y Azure Functions), la separación de los repositorios depende de más comunicación sobre los servicios que se crean.

- Azure App Service - Webapp FrontOffice
- Azure App Service - WebApp BackOffice

- Azure Functions - Serverless para ejecución de tareas en segundo plano

Todo lo que tiene que ver con datos en tiempo real y caché.

# Reflexiones Finales
------------

## Separación de la Infraestructura en Repositorios

- Inicialmente se consideró la idea de hacer la separación estrictamente por los servicios ofrecidos (e.g. todo lo relacionado con almacenamiento en un repositorio, todo lo relacionado con UI en otro repositorio y todo lo relacionado con funcionalidad serverless en el tercer repositorio).
- Finalmente los servicios se agruparon en tres categorías de actividades realizadas (UI, almacenamiento y analítica), de esta forma cada repositorio tiene una responsabilidad única.
- Con este tipo de separación entre los repositorios, habían recursos que se deseaba ser compartidos, pero estaba en repositorios distintos. Esta problemática fue el escenario perfecto para poner en práctica la referencia de servicios desde un repositorio diferente.

## Sistema implementado para el procesamiento asíncrono de tareas en segundo plano

- La aplicación está compuesta por una sola API que es consumida por dos UI, se ha tomado esta decisión porque la UI BackOffice no representará una carga computacional tan grande como la UI FrontOffice.
- Para reducir aún más el consumo de la API por parte del FrontOffice se hace uso de un servicio de Redis Cache. Puede ser usado para manejar la sesión, el carrito de compras e incluso data frecuentada por el cliente.
- También se hace uso de servicio Queue Storage, para guardar en cola las tareas de los usuarios que no exigen una respuesta inmediata (e.g. confirmación de compra, transacciones). Estas tareas o mensajes luego serán ejecutadas por el servicio Azure Functions, que funciona de manera serverless logrando mitigar la carga innecesaria en la API general de la aplicación.

## Uso de un Datawarehouse y herramienta de orquestación ETL

- Una base de datos OLTP donde se guarda toda la información transaccional del negocio, un servicio llamado Azure Data Factory (orquestador) y el Datawarehouse para guardar la información procesada para análisis del negocio, son las herramientas involucradas para la toma de decisiones a partir de los datos.
- Los procedimientos almacenados que forman parte del ETL están alojados en el Datawarehouse, el orquestador simplemente se encarga del flujo de trabajo realizado por el ETL.
- El uso de estos elementos para el desarrollo de un DW es una opción excelente y más económica que otras opciones (desarrollo de IA para análisis de negocio o Azure Synapse Analytics), además, se puede identificar con precisión las estadísticas del negocio por medio de la data procesada.

# Solution Design

![Architecture Diagram](/assets/img/projects/infra-ecommerce/Arquitectura_Nube_Ecommerce.drawio.png)

## Justification of the Architectural Components

- **Two web servers for the UI**. Separate responsibilities between a FrontOffice and a BackOffice, and improve security.
- **SQL OLTP DB**. Host the business's transactional information.
- **BLOB Storage.** Store static content and all of the business's media files.
- **Web server for the API.** Handles access to the business data stores. One API shared by both UIs, since the business-side UI does not demand enough computing cost to justify separate APIs.
- **Queue Storage and Azure Functions.** Handle background tasks that do not require an immediate response, to avoid a high workload on the server hosting the API.
- **Azure Cache for Redis.** Host frequently visited data, the shopping cart and customer session, to achieve a fluid UX.
- **Azure Data Factory and DW**. An orchestrator to handle the ETL process between the business's OLTP DB and the data warehouse that stores data ready for strategic analysis.

### More Detailed Justification of the Services (optional)

- Each type of user (customers, editors) can access from a **UI** on a dedicated server (**FrontOffice and BackOffice**).
- The **UIs** take information from the **SQL database** through a single **API** (it was decided to keep a single API because business management requires a much lower computing cost than that generated by customers).
- The customer UI prioritizes efficiency and a fluid user experience, so it can send messages to **Queue storage** for orders, transactions, etc., which are then executed in the background by a **Serverless** service.
- The customer UI will use **caching (Azure Cache for Redis)** to host information such as the shopping cart, session data and frequently visited information, ensuring a **delay-free user experience**.
- For business analysis, the **Data Factory orchestrator** runs the **ETL process** between the **OLTP database and the data warehouse**, so the data warehouse information can then be requested by the API or an external tool (Power BI), and business management can **perform strategic analysis**.

------------

The resources were separated into business modules, in three different repositories:

- Applications module
- Storage module
- Analytics module

On discovering that resources can be shared (e.g. a database service can be shared by the DW and OLTP databases, a storage account service can be shared by Queue Storage and Azure Functions), the separation of repositories depends on more communication about the services being created.

## Applications Infrastructure Repository

UI and asynchronous tasks

- Azure App Service - FrontOffice WebApp
- Azure App Service - BackOffice WebApp
- Azure App Service - API WebApp
- Queue storage - Queue for tasks without an immediate response
- Azure Functions - Serverless for running background tasks

## Storage Infrastructure Repository

Everything related to real-time data and cache.

- Azure SQL Database - OLTP DB

- Azure Cache for Redis - Volatile data storage

## Analytics Infrastructure Repository

For the data warehouse and ETL orchestration.

- Azure SQL Database - DW

# Final Reflections
------------

## Splitting the Infrastructure into Repositories

- Initially the idea was to split strictly by the services offered (e.g. everything related to storage in one repository, everything related to the UI in another and everything related to serverless functionality in a third).
- In the end the services were grouped into three categories of activity (UI, storage and analytics), so each repository has a single responsibility.
- With this kind of separation, some resources that were meant to be shared ended up in different repositories. This problem was the perfect scenario to practice referencing services from a different repository.

## System Implemented for Asynchronous Background Task Processing

- The application is made of a single API consumed by two UIs. This decision was made because the BackOffice UI will not represent as large a computing load as the FrontOffice UI.
- To further reduce API consumption by the FrontOffice, a Redis Cache service is used. It can be used to manage the session, the shopping cart and even data frequently visited by the customer.
- A Queue Storage service is also used to queue user tasks that do not demand an immediate response (e.g. purchase confirmation, transactions). These tasks or messages are then executed by the Azure Functions service, which works serverlessly and mitigates unnecessary load on the application's general API.

## Use of a Data Warehouse and an ETL Orchestration Tool

- An OLTP database that stores all of the business's transactional information, a service called Azure Data Factory (orchestrator) and the data warehouse that stores the information processed for business analysis are the tools involved in making decisions from data.
- The stored procedures that are part of the ETL are hosted in the data warehouse; the orchestrator simply handles the workflow run by the ETL.
- Using these elements to build a DW is an excellent and cheaper option than others (developing AI for business analysis or Azure Synapse Analytics), and business statistics can be identified precisely through the processed data.
