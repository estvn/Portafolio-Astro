Resumen. La API no tuvo cambios de lógica, por eso las tres alertas siguen igual. La única alta (SQL Injection) es un falso positivo comprobado en la base de datos y cubierto con un test de integración. No se encontró ninguna vulnerabilidad real con ZAP en la API.

  • Menos peticiones en el "después". La diferencia se repitió en dos corridas independientes y no se conoce la causa. Todos los escaneos terminaron al 100 %, así que se lee como "mismas alertas", no como "misma cantidad de pruebas".
  • Base de datos. Cada escaneo "después" partió de la misma base limpia que el "antes".
  • Operaciones con 2xx. En la cobertura del OpenAPI, 62 de 74 operaciones del archivo principal respondieron 2xx; la nota del "antes" dice 63 de 74 para la pasada principal. Es una diferencia de una operación que no se reconcilió. Las que no dan 2xx tienen causa conocida (códigos de reset por correo, invitación en su primera hora, logo binario, change-password excluido).

Límites

  • ZAP no prueba autorización: acceso a datos de otro tenant o de otro rol (IDOR), X-Tenant falso, JWT manipulado, enumeración de usuarios. Eso se cubre con los tests de integración de la API (RLS, RBAC y escalada de roles), no con este escaneo. No hay una prueba manual con curl por rol y tenant registrada: no medido.
  • No se probó la subida del logo del negocio (exige un PNG binario real) ni los códigos de reset enviados por correo.
  • El límite de tasa estaba apagado durante los escaneos.
  • Esta página no incluye los JSON ni los HTML originales de ZAP porque contienen los JWT de las cuentas de prueba.
