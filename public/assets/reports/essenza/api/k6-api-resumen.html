Pruebas de carga k6 de la API

Solo los escenarios de la API: login masivo, API pública que lee la tienda y escrituras con subida de fotos. Todos los números salen de los JSON de k6; cada fila enlaza al dashboard completo de su corrida. Ciclo 2026-11-22, más el primer ciclo del 2026-11-20 para las fotos.

Líneas de paso: fallos < 1 %, API de la tienda p95 < 500 ms, login p95 < 3 s, subir foto p95 < 3 s, crear producto p95 < 1 s. Verde cumple, amarillo hasta 3 veces el límite o 10 % de fallos, rojo más que eso.

1. Entorno y método

PiezaCómo corrió
APIContenedor construido con api/Dockerfile (el de Render), --cpus 0.1 --memory 512m, ENVIRONMENT=production, límite de tasa apagado (todos los usuarios virtuales salen de una IP). Se reinicia antes de cada prueba.
Base y storageContenedores de desarrollo en la misma máquina (un portátil que también corre k6).
Cargas100, 150, 300 y 500 usuarios, 40 s por prueba; escrituras con 5, 10 y 25 usuarios. Una corrida "antes" y una "después" por nivel.
Son números del sistema contra sí mismo en un portátil, no números de producción.

2. Antes

Con el usuario de pruebas (admin2) todavía con el hash de contraseña antiguo (m=65536, t=3, p=4). Ver cada tabla en la sección 4 (columnas "antes").

  • Login masivo: fallos de 84.0 % / 90.6 % / 98.8 % / 99.6 % con 100 / 150 / 300 / 500 usuarios.
  • API de la tienda: p95 de 820 ms a 2.37 s, con 34.9 % de fallos a 500 usuarios.
  • Primer ciclo (2026-11-20): un login con el hash completo costaba unos 3.6 s de CPU y convertir una foto en la API tardaba unos 60 s: con 5 subidas todas llegaban al timeout (27.8 % de fallos) y con 10 el contenedor moría por falta de memoria (60.6 %).

3. Correcciones

Problema medidoCorrección
Login: 3.6 s de CPU por login con 0.1 CPUHash argon2id al mínimo de OWASP (m=19456, t=2, p=1): 3.6 s a 0.7 s por login (10 logins seguidos). Un hash guardado conserva su costo, así que en el ciclo del 2026-11-22 solo faltaba actualizar el hash del usuario de pruebas en la base y en la semilla: un login pasó a 0.7 a 1.2 s. Sin cambio de código en ese ciclo.
Fotos: ~60 s por foto y memoria agotada con 10 subidasEl navegador convierte a WebP (lado máximo 1600 px) y la API solo valida y guarda los mismos bytes. Se probó libwebp con pérdida en la API: 7 veces más rápido sin límite de CPU pero también se quedaba sin memoria con 10 subidas, no se adoptó.
Cola larga de hashesProbado y no adoptado: una cola más corta cambia esperas de 40 s por fallos rápidos pero deja entrar de 13 % a 43 % menos gente. El parche M6 queda guardado sin aplicar porque toca la autenticación.
API de la tienda, ~700 msNo se corrigió: cada endpoint tardó 10 a 40 ms solo en el ciclo anterior; el resto es cola de CPU con 0.1 CPU.

6. Lectura honesta

  • Lo que mejoró de verdad: el login masivo con 100 usuarios (fallos de 84.0 % a 24.9 %) y las subidas de fotos del primer ciclo (de timeout y memoria agotada a p95 de 330 ms / 567 ms / 1.49 s con 5 / 10 / 25 usuarios y 0 % de fallos).
  • Ruido: el resto se mueve sin tendencia entre corridas. Con tres repeticiones, el login masivo con 100 usuarios falla entre 22 % y 31 %, y las latencias p95 varían mucho; diferencias de 100 a 300 ms no son mejora ni regresión.
  • El 500 no pasa: con 500 usuarios fallan entre 35 % y 80 % de las peticiones de la API.
  • El login masivo sigue mal con 300 y 500: 92 % y 97 % de fallos tras la corrección. Con 0.1 CPU caben menos de 2 logins por segundo. Es el límite del plan, no un fallo del código.
  • Limitaciones: un solo "antes" y un solo "después" por nivel, el límite de tasa está apagado y todo corre en un portátil compartido.
