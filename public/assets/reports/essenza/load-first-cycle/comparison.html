EssenzaHn: load tests, before and after

Go API tested with k6 inside a container limited to what Render Free gives (0.1 CPU, 512 MB), local Postgres, one laptop. These numbers compare the system with itself; they are not production numbers. Failed = HTTP 5xx or no answer.

Improvements applied

1. Cheaper password hash at login

Problem found: argon2id with 64 MiB, 3 passes, 4 lanes cost about 3.6 s of CPU per login on 0.1 CPU. The login storm (everybody logs in at once) succeeded for only 31 % of 50 users and 2 % of 100 users.

Change: OWASP minimum profile, 19 MiB, 2 passes, 1 lane (api/internal/shared/security/security.go). Existing hashes keep verifying (the parameters are stored inside each hash) but keep their old cost until the password is set again; rehash-on-login was evaluated and not implemented.

Result (10 sequential logins, 0.1 CPU): 3.6 s → 0.7 s per login (about 5x cheaper). The login storm after the change was not valid as evidence (every user retried with no pause); the sequential measurement is the reliable number.

2. Photo conversion moved to the browser

Problem found: the API decoded, resized and re-encoded each photo with a pure Go WebP encoder: 6.1 s of one core per photo (about 60 s on 0.1 CPU), and 10 uploads at once ran the 512 MB container out of memory.

Change: the back office converts to WebP and limits the longest side to 1600 px before uploading (BACKOFFICE.../productos/image-convert.ts); the API only checks it is a complete WebP, at most 1600 px and 10 MB, and stores the same bytes (api/internal/shared/imaging/webponly.go). Anything else is rejected with a message asking the user to retry (415, 422 or 413). A lossy libwebp build was also measured: 7x faster than the pure Go encoder without a CPU limit, but it still ran out of memory at 10 uploads, so it was not adopted.

Result: one valid upload answers in 157 ms on 0.1 CPU (before: over 60 s); see the table below for 5, 10 and 25 users.

3. Storefront: one render per cold page (request coalescing)

Problem found: when many visitors reached the same page before it was cached, every one of them rendered it, and each render makes several calls to the 0.1 CPU API. With 100 visitors and an empty cache the storefront had p95 13.5 s and 1.9 % failures.

Change: the Worker middleware (store-a/src/middleware.ts) keeps the in-flight render of each URL; concurrent requests for the same URL wait for it and get their own copy. Only plain data is shared between requests (status, headers, bytes), because a Workers Response stream cannot cross requests: the first version shared the Response and 4 of 5 concurrent requests failed with "Cannot perform I/O on behalf of a different request".

Result at 100 users, cold cache: p95 13.5 s → 1.7 s, failures 1.9 % → 0 %, and almost twice the requests served in the same 40 s. At 50 users p95 4.6 s → 2.5 s. Limit: per isolate only; a miss on a new page still costs its own render.

Before and after: API, back office and storefront (50 and 100 users)

Same container (0.1 CPU, 512 MB), same scripts, API restarted before each run. p95 = the time under which 95 % of the requests finished. Pass lines: storefront p95 < 500 ms, back office screens p95 < 800 ms, failures < 1 %. Only the real storefront changed in code (improvement 3); the API-direct and back office rows are the same code run twice, so their differences are run-to-run noise (up to about 2.5x on this laptop), not improvements or regressions. The 150-user level was dropped on purpose: it is beyond what 0.1 CPU is meant to serve.

Back office, why it stays slow: every endpoint answers in 10 to 40 ms when it is alone (products with limit=100 is 46 KB, 57 products; reviews 16 KB), so no single call is heavy. With 100 staff members clicking at once the many small calls queue on 0.1 CPU. That is the capacity of the plan, not a payload bug, so no code change was made. 100 simultaneous staff members is also far above a real store.

Still open

  • Back office screens: p95 above the 800 ms pass line at 100 users on 0.1 CPU (capacity, see above).
  • Not measured: Neon latency and cold start, Render cold start, the storefront in a real browser, the remaining simple write endpoints. Logo uploads with very large noisy images can use about 150 MB each.
  • A WebP that passes the header checks can still be broken inside (a patched header over a short payload): the API validates headers only, by design.

Raw evidence: every results/*.json (numbers) and results/*.html (k6 dashboard); photos in fixtures/; run scripts in runners/; written analysis in RESULTS.md.
